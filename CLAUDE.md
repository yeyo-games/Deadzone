# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Dead Zone" is a top-down 2D zombie survival game that runs in the browser (Chrome/Safari, desktop and phone). It is a static site: plain ES modules built with Vite (no framework). `js/core`, `js/sim` and `js/net` are TypeScript (`.ts`, erasable syntax only); `js/render`, `js/ui` and the root files are JavaScript checked with `checkJs`. The only browser dependency is `@colyseus/sdk`, loaded lazily for online mode. All art and sound are generated in code (`js/render/sprites.js`, `js/ui/audio.js`). UI text, README and game copy are in Spanish; keep new player-facing text in Spanish.

## Commands

- Run locally: `npm run dev` (Vite dev server at http://localhost:8080). Opening `index.html` by double-click does not work because the modules need a server. `npm run build` writes `dist/`; `npm run preview` serves it (4173).
- No stamping: Vite hashes the output files. `js/core/version.ts` exposes `VERSION` (injected at build, `dev` otherwise) and `hayVersionNueva()`, which compares it with `version.json` to show a "new version" toast.
- Publishing: a push to `main` (the default branch) deploys the Vercel project `deadzone` (`deadzone-five-red.vercel.app`). Vercel runs `npm run build` (`vite build` into `dist/`; `vercel.json` sets no-cache on `index.html`/`version.json` and immutable on `/assets/*`); static files that must keep their name (manifest, icons) go in `public/`. GitHub Actions: `ci.yml` checks Biome, the core tests, the Vite build, the server tests and Playwright; `servidor.yml` updates the Vultr VM over SSH (`deploy/actualizar.sh --esperar`) when `server/`, `js/` or `deploy/` change. The `yeyo.games` hub is a separate Vercel project (`yeyo-games`, Astro, deployed with the Vercel CLI, not in git) whose `vercel.json` rewrites `/deadzone/` to `deadzone-five-red.vercel.app`, so it always serves the latest production build.
- Browser game checks: `npm run typecheck` (`tsc -p tsconfig.json` with checkJs plus `tsc -p tsconfig.strict.json`: `noImplicitAny` and `strictNullChecks` on core/sim/net), `npm run lint` (Biome), `npm test` (node:test) and `npm run e2e` (builds, then Playwright against `vite preview`; override ports with `E2E_WEB_PORT`/`E2E_SERVER_PORT`).
- Production server: `wss://servidor.yeyo.games` (`NET.server`), a VM (Vultr, Mexico City, DNS at Hostinger) running `deploy/docker-compose.yml` (server + Caddy for `wss://`); setup and update steps in `deploy/README.md` (`deploy/instalar.sh`, `deploy/actualizar.sh`). `render.yaml` is the old free-tier option.
- Online server (`server/`, its own `package.json`): `npm run server:install` once, then `npm run server` (ws://localhost:2567, `/health`). `npm run server:test` runs the `node:test` suites (rooms, sim, netcode); `npm run build --prefix server` is a type-check only (`tsc --noEmit`). `npm run server:load` runs the load script (5 rooms × 4 bots by default; `--url`, `--origin`, `--rooms 5x4`) against a running server. The server runs `.ts` files directly with Node's type stripping (Node ≥ 22.18), so only erasable TypeScript syntax is allowed (no enums, decorators or parameter properties).

## Architecture

**Layout of `js/`.** `core/` (config, util, version, shared types), `sim/` (game logic that also runs on the server: world, zombies, bullets, build, player, robot, pickups, director, combat, abilities, upgrades), `render/` (all drawing: sprites, lighting, particles and one `<x>.js` per sim module that has visuals), `net/` (client networking: `protocol.js` with the wire tables and `IN_*` bits shared with the server, `netcode.js`, `online.js`) and `ui/` (input, audio, music, accounts, and one module per screen: `hud`, `shop`, `class`, `look`, `levelup`, `over`, `menu`, `account`, `board`, `lobby`, `icons`, `dom`, `tutorial` (the mandatory first-run training: `game.tuto` holds the step; while it is set `updatePlay` does not run the director or save), `manual` (the chained book in the menu, its own `manual` state), plus `dev`: the developer panel, enabled with `?dev=1`, read-only online, and any cheat sets `game.devUsed` so the run is not recorded). At the root: `main.js`, `states.js` (state table), `events.js` (combat events of the local player), `actions.js` (key/button actions), `save.js` (saved progress).

**Entry and loop.** `js/main.js` (about 300 lines) only coordinates: `Game` builds the modules, holds the run state (`money`, `kills`, `inv`, …), runs the loop and exposes, as one-line arrow fields, the `game.xxx(...)` methods that sim, net and e2e code call (`toast`, `killZombie`, `saveProgress`, `closeShop`, …). Everything else lives in modules of plain functions that take `game` as first argument (`openShop(game)`, `Structures.explode(game, …)`). `js/states.js` is the state machine as a table `STATES = { estado: { screen, music, enter, exit, update } }` (`menu`, `manual`, `play`, `pause`, `levelup`, `shop`, `turret`, `over`, `account`, `board`, `look`, `online`, `class`); use `setState(game, name)` and `stepState(game, dt)`, and add a new screen as a new entry. Each UI module in `js/ui/` has a `bindXxx(game)` that wires its own buttons (called from `Game.bindUi`). Adding a method to `Game` that a sim/net module calls means adding the arrow field in `main.js` (`test/estados.test.js` checks it against `GameHost` in `core/types.d.ts`).

**Build and cache.** Vite bundles `js/main.js` from `index.html` and emits hashed files in `dist/assets/` (cached forever); `index.html` is never cached. `@colyseus/sdk` is a dynamic `import()` in `js/net/online.ts` and becomes its own chunk. The server still imports `js/` directly, so modules must not depend on Vite-only features (`version.ts` guards `__DZ_VERSION__` with `typeof`).

**Data and balance.** `js/core/config.ts` holds all tuning (`START` is the soft start: smaller waves 1–3, no SWAT in wave 1, no hit money loss in waves 1–3, cheaper levels 1–2, wave-clear bonus `Rules.waveBonus`): weapons, zombie stats, bounties, shop prices, drops, robot, rocket, golden zombie, Supabase `ONLINE` settings (`url`, `key`). Change numbers there rather than in the logic files.

**World.** `js/sim/world.ts` builds a procedural city in chunks (`setChunkScale`, `maxChunks`), provides collisions (`pointBlocked`, `rectFree`), reachability checks, a flow field toward the player (`updateFlow`), and dynamic obstacles (`addDynamic`) that player-built structures register into. `collide(e, r, passBlocks, ox, oy)` takes where the zombie ended the previous frame (`z.ox/z.oy`): if a push (crowd pressure, a bull's charge) moved its center into or across a wall, it goes back to the side it came from, never out the far side; whoever teleports a zombie clears `ox/oy` (the director with stragglers).

**Horde and waves.** `js/sim/zombies.ts` (`Horde`) runs all zombies: tactics (direct, flank, back-approach), a spatial grid (`horde.grid.query`) used by bullets, explosions, turrets and fire, and attacks. `js/sim/director.ts` drives rounds: a queue of zombie types spawned at the screen edges, a `waiting`/`active` state, and the "next round" button. Zombies nobody sees run `WAVES.offscreen` times faster, a boost that fades over the last `WAVES.offRamp` px before the view (`director.outside`), so they never brake on entering the screen; they only slow down (to 15 %) once touching the player, and stop stumbling within 220 px. No zombie may appear inside a closed player base or within `WAVES.baseGap` px of a built piece: every spawn site (director, stragglers, golden, boss summons, operations, dev panel) checks `World.baseSpot`, which uses `World.inBase` (connected zones of the nav grid with barricades as walls, the largest being the open city; relabelled lazily after `refreshNav`); when the player is walled in, the fallback in `spawnGroup` searches farther out each try. Special rounds (`EVENTS` in config: fog, blackout, stampede, golden rain, armored siege, blood moon) are rolled in `startWave` (`director.event`, `rollEvent`; never two in a row, `director.events = false` turns them off in tests): they change the queue and `speedMult` there, the pay through `Rules.bountyNow`, the golden clock in `Rules.goldenTick`, and the look in `render/lighting.js`; the event ends with the wave and travels online as `ev` (index in `EVENT_ORDER`). Golden zombie and spawn logic live in `main.js` (`spawnGolden`). The rock zombie (`rock`, tuned by `ROCK` in config, from wave 5) walks straight at the player and reacts to what blocks it in `Horde.rockImpact`/`rockThink`: crushes wood; against metal, fences and sandbags it leans and hits them (`ROCK.leanHit`) and only after `ROCK.lean` s on the same piece (`z.leanB`/`z.leanT`) dents and flings metal (`Structures.moveStack`) or pushes fences and sandbags; rams concrete, backs off and rams HESCO/reinforced, and grabs and throws the player (`p.flungT`: the thrown player kills what it touches in `Horde.flungStep`, credited through `p.sid` online). It also smashes trees and cars: `World.smash(o)` removes a static obstacle (`o.smash`, with a reference to its draw `op`), records its id in `world.smashed` (sent online as `wd` by `encodeStatic`, applied with `World.applySmashed`), and `render/world.js` repaints those chunks with `WRECKS`.

**Combat and structures.** `js/sim/player.ts` (movement, stamina, weapons, reload, recoil), `js/sim/bullets.ts` (segment-circle hit tests, piercing), `js/sim/build.ts` (`Structures`: placement on a 20 px grid at a target point within `BUILD.reach` (`placement(game, kind, tx, ty)`; without a point, in front of the player; `snapPiece` sticks it flush and aligned to the nearest piece, or exactly on top of it to stack), stacking via `layer`, damage that targets the top piece, traps, grenades, molotov fires, rockets stuck to fat zombies, sticky bombs (`stickies`, tuned by `STICKY`: they home on the zombie nearest the aim, stick and blow up after 2 s), acid, turrets, explosions). `js/sim/robot.ts` is a pilotable robot that absorbs hits while the player is on board. `js/sim/rules.ts` holds the combat rules shared by `main.js` (through `js/events.js`) and `server/src/sim/ServerSim.ts`: `killZombie` (bounty, loot, golden zombie, fat acid), `hitZombie`, the golden-zombie clock, acid burn, rockets, robot hits and hit money loss; the caller passes hooks for what differs (whose money, who is notified). Change a combat rule there, not in both places. `js/sim/combo.ts` is the kill streak (`p.combo` on each `Player`, tuned by `COMBO` in config): whoever simulates (solo in `events.js`, `ServerSim` online) calls `comboKill` on a kill (its multiplier scales that kill's bounty and XP), `comboBreak` on a zombie hit and `comboTick` each step; the online client only receives it as `cb` (`applyCombo`) and the HUD draws it.

**Upgrades, rarities and perks.** `js/sim/upgrades.ts` lists the level-up upgrades; each has a `rarity` (key of `RARITY` in config: `comun` when missing, `rara`, `legendaria`, `sinergia`) that multiplies its weight in `rollUpgrades`. Each rarity comes from a source (`UPGRADE_SOURCES`, `rollUpgrades(p, level, taken, 3, { source, wave })`): level-ups offer commons and, from `RARITY.rara.fromWave`, rares; killing the golden zombie offers rares; a defeated boss drops the legendary chest (legendaries, plus the synergy you have ready, always first), falling back to rares and then commons. Pending prizes are `game.bonusPicks` in solo (pushed by the golden/boss hooks in `events.js`, saved, shown first by `ui/levelup.js` with `UPGRADE_SOURCES[src].title`, and they do not spend a level) and `slot.bonus`/`slot.choiceSrc` in `ServerSim` (the snapshot `up` ends with `'@golden'`/`'@boss'`, read by `online.upSource()`). Common ones only change numbers in `p.stats`; the others set perk stats (`burn bounce bounceKeep vamp greed frenzy twin volatile lastStand inferno`, tuned by `PERKS`) that `js/sim/perks.ts` applies from shared code: `Player.tryFire` (`frenzyMult`, `extraShots`, `shotExtras` add fire and bounces to the bullet), `Bullets.update` (`bounceTarget`), `Rules.hitZombie` (marks `z.shotKill` when a bullet of a player's gun finishes it), `Rules.killZombie` (`onKill` with `game.ownerOf(z.lastOwner)`; its explosions go through `structures.queueDeathBlast('perk', …)` → `perkBlast`), `Rules.bountyNow` (greed) and `Player.hurt` (`lastStand`, once per wave via `p.lastStandWave`). Synergies use `when` to require both perks they combine. `frenzy` and `twin` travel in `STAT_KEYS` so the online client predicts its shots; bounced bullets (`b.bounced`) are sent back to their owner in the snapshot.

**Special zombies.** `spitter`, `screamer`, `digger` and `jumper` (stats in `ZOMBIES`, tuning and first wave in `SPECIALS`/`SPECIAL_ORDER`, counted by `waveCounts`, appended at the end of `TYPES` in `protocol.ts`) behave through `js/sim/specials.ts`, called from `Horde.update` (each `…Think` returns true while the zombie does not walk). The spitter winds up (`z.bs = 'windup'`, which the snapshot already flags) and pushes a `Lob` with `kind: LOB_ACID` into `h.lobs` (drawn green by `render/bosses.js`, lands through `updateBossWorld` and leaves a `toxic` zone); the screamer gives nearby zombies the bosses' `buffT`/`buffK`; the digger travels `z.under` (hidden, not in the grid, no collision) straight at you and emerges with `areaHit` after a dust warning; the jumper uses `tryJump` from the collision pass to leap a single-layer block (`z.bs = 'leap'`, height in `z.air`) and ignores wires. Their art is in `render/sprites.js` (`drawSpitter`…), their pages in `ui/manual.js`.

**Escape mode (Huida: a trip of stops, solo and online).** The menu button `#btn-escape` sets `game.runKind = 'escape'`; `start` then uses a detached `Solo` (not saved, no records), remembers `game.lastKind` (restart repeats the mode) and calls `game.escape.begin(game)`. `js/sim/escape.ts` (`Escape`, tuning in `ESCAPE`) places the van (a low dynamic obstacle plus a `makeGoal` target, like the convoy truck), the fuel cans, crates and medkits (their `t` is set very negative so they never expire), and runs the phases `search` → `fuel` (hold H at the van with enough cans; part of the horde gets `z.goal` = the van) → `ready` → `leaving` (`p.inVan`: no damage, not drawn; the van smashes cars and trees with `world.smash` and runs zombies over) or `lost` → `done`, ending through `game.onEscapeEnd` → `ui/escape.js` `escapeEnd` → the over screen. There are no waves: `director.state = 'escape'` makes `Director.update` return, and the escape fills `director.queue` with types sampled from `waveCounts(level)` and calls `spawnGroup`; the threat level rises every `ESCAPE.levelEvery` s and is written to `director.wave` (zombie hp/speed). Drawing is `render/escape.js` (van, cans, beams, fuel gauge, edge arrows, and lights hooked into `lighting.js`); the HUD is `#esc-hud` (`updateEscapeHud`), and the H prompt goes through the operations' `#op-use` (`escapePrompt`). The trip (stage 2): `js/sim/route.ts` `makeRoute(seed)` builds a seeded layered map (`ESCAPE_ROUTE.layers`; first layer `start`, last `bridge`, middle layers 2-3 stops of the `ESCAPE_STOPS` kinds, each with an optional `EVENTS` modifier); `Escape` keeps `route`, `at`, `visited` and `stop`, and per stop derives `need`, `baseLevel`, `payK` (read by `Rules.bountyNow` through `game.escape`) and the kind's extra cans, crates, meds and spawn rate; `begin` sets `director.event` to the stop modifier and heals `ESCAPE_ROUTE.restHeal` of the missing health after the first stop. Leaving a non-final stop ends with `onEscapeEnd('stop')` → `ui/escape.js` fades (`#esc-fade`) to the `route` state (`ui/route.js`, `#screen-route`, drawn by `render/route.js`: `drawRoute`, `drawStopArt`), which saves the trip (`saveTrip`, key `<saveKey>-huida`; `packPlayer`/`applyPlayer` in `save.js`), opens the shop (`game.shopReturn = 'route'` makes `closeShop` come back) and travels: `nextStop` makes a new world with `route.seed + id * 7919`, clears horde, bullets, pickups, structures and effects, keeps the player, and calls `Escape.travel` + `begin`. The menu shows `#btn-esc-continue` while a trip is saved (`loadTrip`). At the bridge, starting to fuel spawns a boss from `ESCAPE.boss.pool` that blocks boarding until it dies; records per account are in `<saveKey>-huida-best` (`recordEscape`). Van upgrades (`VAN_UPS`, order `VAN_UP_ORDER`) live in `Escape.ups` for the whole trip (saved with the trip) and are bought in the route screen's garage (`#route-garage`, `upCost`/`buyUp`; online through `'buy'` with `k: 'van'`, only during the vote, paid by the buyer): armor (van hp and less damage per hit), a roof turret that fires during `fuel`/`ready` (`updateVanUps`; online clients get its shots through `onTurretShot`), a horn usable once per stop with H (`honk`: `stumbleT` and knockback), a bigger tank (`needAt`: one can less) and lights (zombies near the van get `z.dazzleT`/`dazzleK`, read by `Horde.update`). Each stop kind can have an objective (`ESCAPE_STOPS[k].obj`, tuning in `ESCAPE_OBJ`, state in `Escape.obj`, placed by `placeObj`, run by `updateObj`): the gas pump fills a can every `pump.t` s while someone stands in its zone; the clinic medic follows the nearest player and boards at the van (`Escape.medic`: full heal between stops; zombies touching him hurt him); the police armory opens with H held (`openArmory`: the best `armory.guns` weapon under the stop's cap, hook `escapeGun` online); the market's supply bags are sold when leaving (`cart.pay` × stop). H actions share `holdT` and go through `prompt`, which returns `k` (fuel, board, horn or armory). Online, `ServerSim` (`mode === 'escape'`) runs the same `Escape` for all players (`escapePay`/`escapePick` hooks), opens a vote between stops (`'route'` message, `hv` in the snapshot, `stepVote` → `nextStop`) and sends the escape state as `hu` (`packEscape`/`unpackEscape`: route, phase, cans, barrels, van, upgrades, objective); the client applies it in `onlineEscape`. In the escape the shop only opens from the route screen and only sells weapons, ammo and throwables (also enforced in `ServerSim.shop`); weapons with `escape: true` (revolver, dual SMGs, crossbow, grenade launcher, railgun, appended to `WEAPON_ORDER`) are sold only there, and owned weapons can be upgraded up to `WEAPON_UP.max` levels (`Player.upgrade`, `WeaponSlot.lv`; `upDmg`/`upMag`/`upReload` scale damage, magazine and reload; price `weaponUpCost`; online `'buy'` with `k: 'wup'`, level sent as the 4th number of each `wp` entry and saved by `packPlayer`); the level shows as stars in the shop and HUD and gold bands on the gun (`drawGunLevel`). The H prompt `#op-use` can also be held with a finger or the mouse (`input.touchUse`). Travelling from the route screen needs a second press to confirm (`view.confirm`). Any random order in `route.ts` must use the seeded `shuffle`, never `sort` with a random comparator: the browser and the server must build the same route.

**Bosses.** Every `BOSS.every` waves the director puts the next `BOSS_ORDER` boss (15, then the list loops with `BOSS.loop` more hp per lap, `bossLoop`) first in the queue (`bossFor`, half horde via `BOSS.support`, never a special round) and spawns it through `spawnBoss` (hp × `bossHp(players, loop)`, which includes `BOSS.hp`; `z.dmgK = BOSS.dmg` scales its melee and attack hits, and boss zones also scale by `BOSS.dmg`; `choose` arms the attack through `scaled(a)`, which applies `BOSS.power`/`area`/`push`/`wreck` to hit, radius/width, push/throw and barricade damage, so `z.atk` is that scaled copy and `z.ai` the index in the def). Every boss impact goes through `quake` (`particles.quake` shockwave, `decals.crack` ground crack, shake, `sfx.bossQuake`); boss melee hits call `bossPunch`. A walking boss that barely moves in `BOSS.stuck` s, or stays farther than `BOSS.farD` without closing in for `BOSS.far` s (not while biting a barricade, `z.blockT` set in `bossImpact`), does an `escape` leap over everything to a free spot near the player (`landing`, never a `baseSpot`). Bosses are zombie types with `boss: true` in `ZOMBIES` (built by `bossZ`, index in `TYPES`), tuned by `BOSSES[type]` (`BossDef`): a list of attacks (`BossAtk`, each a generic kind `k`: charge, ring, lob, line, summon, buff, self, zone, burrow, leap, pull, emp, walls, revive) plus passives (back/front damage, fury, trail, heal, hunger, stagger, swarm and a breakable `part`). `js/sim/bosses.ts` is the engine: `bossThink` (from `Horde.update`; states `walk`/`windup`/`charge`/`act`/`under`/`leap`/`recover`) picks an attack by range, phase and cooldown, telegraphs it and fires it; `bossImpact` handles charges after collisions; `bossDamage` (called by `bulletHit`) applies back/front/self/vuln multipliers and damages the part; `updateBossWorld` lands `horde.lobs` and runs `horde.zones` (`BOSS_ZONES`), which hurt and slow players (`p.slowT`/`slowK`, read by `Player.move`; sent online as `st[13..14]`); `onFallen` (from `Rules.killZombie`) feeds `horde.fallen` and healing. Temporary walls are `Structures.addTemp` blocks with `tempT` (not saved) and EMP sets `b.empT`. What is drawn travels in every snapshot as `bo` (`bossStatus`, `STATUS_N` per boss) and `bf` (`bossFx`, `FX_N` per row) via `encodeBosses`, and zombie flags 128/256 (under, cloak); the client decodes them into `game.bossNet`, so `render/bosses.js` (`bossView`) and the HUD bar draw the same in solo and online. Boss figures live in `render/bossart.js` and are built lazily (`bossSprite`). A killed boss pays `reward` to every player through the `boss` kill hook. Add a boss by adding its `bossZombies` and `BOSSES` entries, its id to `BOSS_ORDER`, `TYPES`, `ZOMBIE_VARIANTS` and `BOUNTY`, and its figure in `bossart.js`; a new attack kind goes in `fire` (and maybe `choose`/`windingUp`).

**High-risk operations (`js/sim/ops.ts`).** Optional encounters during the break after wave 20 and every 5 (`OPS` in config): a radio offer of two of the three, prep (zone marked, shop open), active (from the first use of the objective), resolve (fade, cleanup of the op's own zombies and obstacle, everyone back home). The director stays `waiting`, so waves and bosses are untouched; `onWaveCleared` calls `ops.afterWave`. `Ops` is the common controller (offer and votes, budget-limited reinforcements from `composition(wave+1)`, spots used by holding H, single payment by op id, serialize/restore); each op is an `OpDef` in `js/sim/ops/{convoy,nest,supply}.ts` on top of `js/sim/ops/common.ts` (route-based placement, `Goal` objects that some zombies attack instead of a player via `z.goal`). Plans won (`decoy`, `repair` pieces and the heavy turret's `fire` upgrade) live in `js/sim/plans.ts` and `heavy.ts`. Whoever simulates provides hooks on `game`: `opsWho`, `opsPay`, `opsToast`, `opsForbids`, `opsMoved`, `opsDone` (solo in `events.js`, online in `ServerSim`). H is `input.useHeld()` locally and the `IN_USE` input bit online; votes and retreat go as the `op` message. `ops.view()` is what HUD and drawing read (`opsView(game)`; online it arrives as `op` in each snapshot and `remote.applyOps` mirrors the obstacle and the local cargo); `ui/ops.js` and `render/ops.js` only read it. Tests: `server/test/ops.test.ts`.

**Rendering.** `js/render/scene.js` draws each frame in world space with the camera of `js/render/camera.js` (shake and kick) and also resizes the canvas and adapts quality; `js/render/lighting.js` handles darkness, flashlight and lamps; `js/render/particles.js` handles particles and ground decals; `js/render/death.js` is the cosmetic death scene of the local player (`startDeath` from `events.onPlayerDeath` and from `online.ts` when `st[2]` turns dead, `updateDeath` from `updatePlay`/`online.update`: bites with `particles.bite`/`guts`, `sfx.chomp`, then a gut burst; `DEATH` in config sets its length, which is also `game.deathT`, and the `DEATH.feast` speed at which nearby zombies run to the body in `Horde.update`); `js/render/floaters.js` (`game.floaters`) draws the +$/+XP numbers that `events.js` adds on each kill (online, `online.ts` adds them when `st[7]` money goes up); in solo `events.js` also sets `game.hitstop`, which pauses the `play` state a few hundredths of a second after a heavy kill or four quick kills; `js/sim/pickups.ts` for ammo, medkits, and crates. `js/ui/input.js` unifies keyboard, mouse and touch (`input.mode === 'touch'` toggles the touch UI class on the root). Touch controls: fire, swap, reload and the ability button are fixed; the context buttons (throwables, build, robot, workshop) live in `.titems` and are `gone` unless usable (`hud.js`); there is no run button (pushing the joystick past `JOY_RUN` runs). Building is a mode (`game.building`, `toggleBuild`/`stepBuild`/`buildTarget` in `actions.js`): `#build-bar` lists owned pieces, the ghost follows the mouse (or the tapped point, else in front along `legAngle`), click/tap/✓ places, and `input.blockFire` stops shooting meanwhile; online the build act carries `tx`/`ty` (`at`). The improvised missile (`SHOP.improv`, `IMPROV`) is a throwable like the grenade (`tryGrenade(game, 'improv')`, server `throw` act) that launches an `improv` bullet (`improvMissile`, `Structures.launchImprov`/`improvBlast`); it travels in snapshot bullets with rocket flag 2 and is not skipped for its owner.

**Persistence and accounts.** `js/ui/accounts.js` manages accounts (name + 4-digit PIN), per-account localStorage keys (`saveKey()` for the rolling save, `checkKey()` for the checkpoint written at the end of each wave), and personal bests. Saves happen on a timer, at wave end, and on `pagehide`/`visibilitychange`. Dying deletes the run save but keeps the record. When the game runs as a Claude Artifact with a database, `accounts.js` also mirrors saves and scores to the cloud (`cloudSave`, `cloudPull`, `cloudClear`); outside Artifacts that path is inactive. The global leaderboard lives in Supabase (table `scores`), reached through its REST API by `js/net/supabase.ts` (no client library; `rpc()` calls the `dz_*` Postgres functions, `select()` reads `scores`); `ONLINE.url` and `ONLINE.key` (the publishable key) in `js/core/config.ts` must be set for it to work.

**Modes, remote view and snapshots.** There are two game modes for the player: «Un jugador» and «En línea · 2 a 4» (a room of 2 to 4 people through the server; playing with a friend is creating a room and sharing the code or the `?sala=CODE` invite link). The old direct P2P co-op (WebRTC + Firebase signalling) no longer exists. `game.mode` (`js/net/mode.ts`) is one of `Solo` (also `detached`: a solo run that came out of an online room, never saved), `OnlineClient`, or `ServerMode` (what the shared sim modules see on the server). Ask it by intent, not identity: `authority()` (this device computes damage; false means local bullets are cosmetic), `inGroup()`, `savesProgress()` (only `Solo` that is not `detached`: progress saving belongs to «Un jugador» alone), `canBuild()`, `viaServer()`, and the request helpers `sendBuild/sendThrow/sendAbility/sendNextRound`. `resetRun()` always starts `Solo`; `online.ts` switches the mode when a room game starts and goes back to `Solo` `detached` when the player leaves. Do not add `coop.isHost`-style checks or `game.coop` (`test/llamadas.test.js` fails on them). `js/net/snapshot.ts` is the single encoder of the world part of a snapshot (`z zx zh o pl rb pk b gr fi so sb ms bl w ds tm ev`, plus `encodeStatic` for `blk wir sc`), used by `ServerSim.snapshot`, which adds the online fields (`me st wp ec ps iv ab hv up fx tt dg ml lft kl cb`). `js/net/remote.ts` (`game.remote`) decodes it for the online client: zombies and other players move with `Interp`, robots/pickups/bullets/structures/effects are applied the same way; `js/render/remote.js` draws peers and cosmetic bullets.

**Online mode (2 to 4 per room, 8 rooms, authoritative server).** `server/` is a Colyseus 0.18 server. `server/src/rooms/DeadZoneRoom.ts` owns the lobby (Schema state in `state.ts`: members, ready, owner, phase `waiting`/`loading`/`playing`/`finished`), capacity (`MIN_PLAYERS` = 2 connected members needed to start, `MAX_PLAYERS` = 4 per room, `MAX_ROOMS` = 8 rooms per process: `onCreate` throws `servidor-lleno`; idle lobbies close after `IDLE_ROOM_MINUTES`), origin and name checks in the static `onAuth` (runs at HTTP matchmaking, before a room is created), validation and rate limits (`validate.ts`), reconnection (`onDrop` → `allowReconnection`, same `sessionId`) and a fixed-step loop with bounded catch-up. `server/src/sim/ServerSim.ts` runs the real game modules headless (nothing under `js/core`, `js/sim` or `js/net/{protocol,netcode}` touches `document`, so no shim is needed) for N players: it is the `game` object those modules see, sets `game.targets` (players) which `Horde.update` and `Pickups.update` use instead of `game.player`, records particles/sfx/decals as effects for nearby clients, and builds per-player snapshots. Clients send only intents through Colyseus 0.18's input channel (`room.input()` on the client, `defineInput(MoveInput)` in `DeadZoneRoom`; `MoveInput` is in `server/src/input.ts`: `mx my f a w`, sanitized by ranges, reliable mode over WebSocket); the framework counts consumed inputs (`consumedCount`), which is the ack and the input seq (`cmd.s`), and `ServerSim` pulls them one at a time through `slot.port` (ask `this.inputs.get(id)` every time: after a reconnect the SDK gives a fresh buffer). Never trust client positions or hits. `js/net/online.ts` is the client: lobby, fixed 60 Hz input with prediction/reconciliation of the local player (the SDK's `predict.reconciler` over the player's `Body` Schema in `state.bodies`; its `step` is `applyMove` → `Player.move`; the ack travels with the state patches, `setPatchRate(1000 / snapHz)`), interpolation of others and zombies (`Interp`), effect replay and diagnostics. `Player.update` is split into `move` (shared by server and prediction; keep it deterministic and input-only) and `act` (aim and weapons). Bullet-hit rules live in `js/sim/combat.ts` and are used by both `main.js` and the server. The flamethrower (`WEAPONS.flamer`, which replaced the rifle; saves with `rifle` get it in `save.js`) fires `flameBullet`s (`flame`, `burn`, `life0`) that pierce every zombie, set `z.burn` and are skipped from the snapshot bullets; clients draw other players' flames from the fire flag in `pl` (`RemoteWorld.peerFlames`, `fake` flames that do no damage). `!game.mode.authority()` is true for an online client: local bullets are cosmetic. The simulation tick rate is `NET.tickHz` in `js/core/config.ts` and must match on both sides; other online tuning is in `NET` and in `server/.env.example`. Between waves each player toggles ready (`'next'` message → `ServerSim.ready`; `rd` in the snapshot = ready, of, me) and the next wave starts only when every connected player is ready (`tryNext`, no auto-start). Level-ups, the shop, building, throwables and the robot are server-authoritative online: each `Slot` in `ServerSim` has its own money, level/XP (XP is shared by the team, bounties go to the killer), pending upgrade choices (`choices`/`choiceN`, sent as `up` in the snapshot; offered mid-wave too, the client shows a `#btn-upgrade` button/U key instead of pausing), inventory `inv`, a `Robot`, and handlers `pick`/`shop` (shop only between waves). The heavy turret (`SHOP.heavy`) is mounted through the same `robot` act (`Structures.mountHeavy`/`leaveHeavy`); while `p.manned` is set, `Player.move` pins the player behind the cannon and `Player.act` fires the turret's ammo (`p.heavyAmmo`). Each heavy turret has its own upgrades (`HEAVY_UP` in config: calibre, cadencia, carga explosiva, blindaje, piloto automático), packed as 4 bits per upgrade in `b.up` (saves without `upBits: 4` are widened by `widenHeavyUp`) and read through `js/sim/heavy.ts` (`heavyLevel`, `heavyDmg`/`heavyRate`/`heavyBlastR`/`heavyMaxHp`, `upgradeHeavy`, `fireHeavy`, shared by the manned shot and the autopilot `updateAutoHeavy`, which spends the owner's ammo through `game.ownerOf`). They are bought next to the turret in the workshop (`js/ui/turret.js`, state `turret`, M key or `#btn-tup`; online `buy` with `k: 'tup'`, allowed mid-wave), travel as the last field of each `blk` row and are saved with the blocks. Blast bullets carry `blastR`/`blastP` to `game.heavyBlast`. The military turret (`SHOP.military`, tuned by `MILITARY`) is automatic (`Structures.updateMilitary`, big zombies first) and fires anti-tank missiles: bullets with `atgm` built by `militaryMissile`, which explode through `Structures.missileBlast` (the Bomber blast) on the first zombie or wall or at the end of their `life`; online the server records `onMilitaryShot` as effect `t`/`atgm` and each client flies a `fake` one that does no damage (missiles are skipped from the snapshot bullets). It can be mounted like the heavy turret (`nearHeavy` and `heavyFor`, the workshop, cover both kinds): the player sits on top (`MILITARY.seat`, not collided with the world while `p.manned`) and `Player.actMilitary` fires through `Structures.fireMilitary` (only with authority; online at full range because the server knows only the aim angle); others see it through `hv`. Online only the owner (`b.owner`, the slot id, compared with `p.sid`; the client sets `p.sid` to its `sessionId`) may mount a turret unless it is shared (`b.shared`, `mayMount`, `nearHeavy(p, any)`): the owner toggles it with the `share` act (L key, `#btn-share`, or the workshop's `#btn-tup-share`; the act carries the turret's `tx/ty`), `Structures.toggleShare` dismounts a non-owner when sharing is revoked, and `blk` rows carry owner and shared after `up`. The military turret has its own workshop upgrades (`MILITARY_UP`/`MILITARY_UP_ORDER`: ojiva, cargador, radar, blindaje, salva) in the same `b.up` bits: `heavy.ts` picks the table by `b.kind` (`upDefs`/`upOrder`; `heavyMax(b, id)` takes the turret) and reads them with `milDmg`/`milBlastR`/`milReload`/`milRange`/`milTurn`/`milSalvo`; `fireMilitary` fires `milSalvo` missiles in a fan carrying `blastK`/`blastRK` to `missileBlast`. Missile trails are `particles.streaks` (glowing segments that fade and also cut the darkness in `lighting.js`). The client sends `'pick'`/`'buy'` and `'act'` (`build`/`throw`/`robot`, tagged with the last input seq `s`; the server runs it when it reaches that input) and gets (besides the shared world part, `pl` now 19 numbers per player and `rb` 8 per robot) money in `st[7]`, acid and in-robot in `st[8..9]`, heavy-turret ammo and the manned turret's position in `st[10..12]`, other players' manned heavy turrets and autopilot turrets (player index 0) in `hv`, `ec`, `ps` (`STAT_KEYS`), `iv` (inventory in `SHOP_ORDER`), `rb` (robots), `gr`/`fi`/`so`/`bl` and, when they change, `blk`/`wir`/`sc` back. The server uses the real `Structures` (`build.js`), so code there must not assume a single `game.player` (use `game.targets` when set). While online, `online.update` runs even under the level-up/shop/pause screens: the world never pauses.

## Supabase (leaderboard and usage statistics)

`supabase/esquema.sql` is the whole schema (idempotent; pasted in the project's SQL editor): tables `scores`, `sesiones`, `partidas`, `elecciones`, `compras`, `config`, all with RLS and no write policies, so the browser writes only through the `security definer` functions `dz_record`, `dz_sesion`, `dz_partida`, `dz_eleccion`, `dz_compra`; `scores` is the only table readable with the publishable key. `estadisticas(clave, desde)` returns every aggregate the stats page draws after checking the key against the bcrypt hash in `config` (set by the owner with `select fijar_clave('…')`, not callable from the API). The `v_*` views are for browsing in the Supabase panel (`security_invoker`, not readable from the API). If you change what the game sends, change the matching `dz_*` function and the README section «Clasificación mundial y estadísticas» together.

**Usage statistics (`js/analitica.js`, `game.analitica`).** Anonymous: a random device id in localStorage (`dz-dispositivo`, never the account `uid`), one `sesion` per page load (heartbeat every minute and on `pagehide`/hidden with `fetch keepalive`), one `partida` per run (`iniciar(modo, id?)` from `start`, `loadProgress` (same id kept in the save as `partida`) and `online.startPlay`; `guardar` on wave end and heartbeats; `muerte(causa)` from `onPlayerDeath` and the online death; `terminar('fin'|'abandono')` from `online.stopPlay`), plus `eleccion` from `chooseUpgrade` and `compra` from the shop. The cause of death is `Player.lastHit` (zombie type, `bull_charge` or `acid`, set by `zombies.ts`/`rules.ts` right before `hurt`); online the client only knows `acid` or `desconocida`. Nothing is sent when `VERSION === 'dev'`, under Playwright (`navigator.webdriver`), without `ONLINE` configured, or after opening the game with `?sinstats` (remembered in `dz-sinstats`). Online runs are reported by the client (purchases and upgrades at the moment of the request). The stats page is a second Vite entry, `stats.html` + `js/stats/pagina.js` + `css/stats.css`, served at `/stats` (`yeyo.games/deadzone/stats` through the hub rewrite, which does not forward a trailing slash, so `vercel.json` rewrites the slash-less path to `stats.html`, redirects the slashed one and sets `noindex`); it keeps the key in localStorage and calls `estadisticas` with a period of 7 days, 30 days or all.

## Conventions

- Plain ES modules with `import`/`export`; Vite compiles the `.ts` modules and Node runs them with type stripping, so imports of those files use the `.ts` extension and only erasable syntax is allowed (no enums, decorators or parameter properties). Class fields assigned in the constructor are declared with `declare name: T;` (erased at runtime). Do not add `any`; shared shapes (`Cmd`, `Act`, `Snapshot`, `LobbyMember`) live in `js/core/types.d.ts` and the server imports them from there.
- Comments and UI strings are in Spanish; the code is otherwise terse and written in the same style as the surrounding file.
- Drawing lives in `js/render/<x>.js`, next to the logic module `js/sim/<x>.js` (e.g. `render/build.js` draws what `sim/build.js` simulates), never in the same file as the logic and not in `main.js` (the frame itself is `render/scene.js`). `js/core/` and `js/sim/` must load in Node without `document` and must not import `js/render/` or `js/ui/` (`test/carga.test.js` enforces it). World generation produces only data (`ops`, trees as seeds); `render/world.js` turns it into images.
